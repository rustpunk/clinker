# Error E374: a log directive requests a field the record does not carry

## What it means

A transform log directive's `fields` list names the record columns whose
values are attached to the emitted event. One of the requested selectors names
no column of the transform's **input** row, so the event would publish without
that attribute — indistinguishable from a run in which no record ever had a
value for it.

Clinker rejects the pipeline before execution rather than emitting events that
quietly say less than the author asked for.

## Example

```yaml
# Rejected: the source declares `order_id`, the directive requests `orderId`.
- type: source
  name: orders
  config:
    path: orders.csv
    format: csv
    schema:
      columns:
        - { name: order_id, type: string }
        - { name: amount, type: decimal }
        - { name: region, type: string }

- type: transform
  name: enrich
  input: orders
  config:
    cxl: "emit amount = amount"
    log:
      - name: transform.order_seen
        level: info
        when: per_record
        every: 1
        message: "order seen"
        fields: [orderId]
```

```
[E374] transform `enrich` log[0].fields requests `orderId`, which the input
record does not carry; the upstream row has `order_id`, `amount`, `region` —
write `fields: [order_id]`
```

## How to fix

Request a column the input row declares. The diagnostic lists the row's
columns and, when the requested spelling is close to one of them, names the
column it most likely meant — paste that `fields:` line in place of yours.

```yaml
        fields: [order_id]
```

Two shapes account for most of these:

- **A spelling slip.** `orderId` for `order_id`, `custId` for `customer_id`.
  Column names are matched exactly; case and underscores are significant.
- **A column the transform produces rather than receives.** Dispatch runs
  before the transform's own `cxl:` block, so a directive sees each record as
  it arrived. A column the transform computes is not available to `fields:`.
  Request the inputs it is computed from, or attach the directive to a
  downstream transform that receives the computed column.

A dotted selector such as `customer.id` is matched as a single flat column
name, not as a path into a nested value. It resolves only if the input row
declares a column literally named `customer.id` — which flattening readers do
produce for nested JSON and XML sources. If yours does not, the selector names
nothing and is refused here.

## Technical context

The check runs against the transform's input row, for both `when: per_record`
and `when: on_error` — dispatch fires before the transform's program in both
cases, so the record a directive reads is the one that arrived.

It decides only what a **closed** row can decide. A row left open at a
composition port carries columns declared outside the planner's view, and a
selector naming one of those cannot be refused at compile time. Those misses
are counted at runtime instead and reported as
`observability.admission.fields.missing` in the machine terminal and on the
admission line.

`fields` is separately capped at 256 selectors per directive and 256 across
one transform, and each selector must be a bounded dotted identifier.
