# Error E310: a memory surface exceeded the hard memory limit

## What it means

At runtime, one of the engine's memory surfaces crossed the hard limit
set by `memory.limit` and could not spill its way back under. The run
aborts rather than letting the process get OOM-killed.

E310 is the engine-wide memory-budget code, not a per-operator one. Many
different surfaces raise it — join hash tables, grouped record buffers,
inter-stage handoff buffers, per-operator decision state. **The
diagnostic tells you which one.** Read it before picking a fix:

```
E310 <node>: <category> exceeded budget (<used>/<limit>) [<detail>]
```

- `<node>` is the pipeline node that was holding the memory.
- `<category>` is `arena` (any budgeted allocation) or `node_buffer`
  (the handoff layer between stages).
- `<used>` / `<limit>` are bytes. `<used>` is sometimes one surface's own
  footprint rather than the whole run's, so treat it as a floor for how
  much headroom you need, not a target.
- `<detail>` names the specific surface. This is the part that selects
  your remedy.

A well-tuned pipeline rarely sees E310: most surfaces spill to disk long
before the hard limit. E310 means spilling was impossible, insufficient,
or already exhausted.

## Example

E310 is a runtime condition, so it carries no source span and no
`error[E310]` header — the code appears at the start of the message
itself:

```
E310 drop_big: arena exceeded budget (512000/8192) [one Cull correlation
group [account="BIG"] does not fit; the reported use (512000 bytes) is
that group's reload footprint alone. ...]
```

Grep CI logs for `E310`, not `error[E310]`.

## How to fix

Read the `[detail]` first, then apply the matching remedy.

### Universal first resort

**Raise `memory.limit`** if the host actually has the memory. It is the
only remedy that never changes your output:

```yaml
pipeline:
  memory: { limit: "4G" }
```

The suffix must be a bare `K`, `M`, or `G` (binary units). Spellings
like `4GB` or `4 GiB` are **not** accepted, and in YAML an unparseable
value is currently replaced with the 512 MiB default instead of being
rejected — so a typo here shows up as an abort reporting a limit you
never set. See issue #1026.

Raise it clear of the reported `used` figure — in the per-surface cases
below, other state is resident at the same time.

### Combine and join surfaces

Details mentioning `combine`, `grace hash`, `iejoin`, or `sort-merge`:

1. **Add a `drive:` hint** so the smaller input builds the hash side:
   ```yaml
   - type: combine
     name: enrich
     input: { orders: orders, products: products }
     drive: "products"                  # small reference data
     where: "orders.product_id == products.id"
     cxl: |
       emit orders.id, products.name
   ```
2. **Pre-filter the large input** with an upstream `transform` so fewer
   rows reach the probe side.
3. **Narrow the predicate.** A band or inequality join spreads work
   across disk-backed blocks, but one indivisible block pair must still
   fit the budget on its own.

### Grouped record buffers (Reshape, Cull)

Details naming a specific `correlation group [...]`. These operators
evaluate rules against a *whole* group at once, so one group must fit
even though cross-group and ingest-time peaks spill.

If the printed group name does not match any value you can find in your
input, note that integer keys are currently rendered via `f64`, so a key
above 2^53 prints rounded — see issue #1024.

Raise `memory.limit`. Two other levers shrink the group but **change
your results**, so weigh them deliberately rather than reaching for them
to clear the error:

- Dropping unread columns upstream shrinks each record, but both nodes
  write every input column through, so those columns also leave the
  output.
- Narrowing `partition_by` redefines the group the rules evaluate over,
  which changes which records each rule sees.

### Operator decision state

Details such as `Cull drop-decision aggregate state` — per-group state
that is `O(distinct groups)` and cannot spill. Raise `memory.limit`, or
coarsen the partition key **if** the coarser key is the grouping you
actually meant.

### Oversized aggregate rows

`a single buffered aggregate row's ... footprint exceeds the whole ...
budget` — one input row is larger than the entire budget, so spilling
cannot help; re-reading it would repeat the overflow. The budget is
almost certainly far too low for the record shape.

### Handoff buffers

Details such as `non-spillable node-buffer admission`,
`re-materializing spilled node buffer`, or a `cross-region tee
admission`. A stage that fans out to more than one consumer, or that
feeds a composition input port, must hold its rows in memory for those
consumers to read, so it never spills.

Raise `memory.limit`, or restructure so the shared stage feeds a single
consumer.

## Technical context

The `MemoryArbitrator` runs a dual-threshold budget: a soft limit (0.80
of `memory.limit` by default) triggers spilling in the operators that
can spill, and the hard limit aborts. A separate spike allowance
tolerates brief fan-out bursts. Soft-limit crossings cause spill, not
E310.

Surfaces reach the hard limit by different routes — some poll process
RSS, some track their own charged bytes, some weigh a single allocation
against the whole budget before admitting it. That is why `used` is not
uniformly "the whole run's memory": for a single-allocation refusal it
is that allocation's own size.

The sections above cover the surfaces with dedicated guidance. Because
every budgeted allocation in the engine charges the same counter, other
surfaces can raise E310 too — the `[detail]` string, not this page, is
the authority on which one overran.

## Composition involvement

A composition (a reusable sub-pipeline included via `use:`) shares the
**same** `MemoryArbitrator` as the parent pipeline — there is one budget
per run, and body operators charge it through the same admit and spill
paths every other node uses. The split below is about *which name*
appears in the diagnostic, not about asymmetric enforcement.

1. **Boundary admit (bare error).** Records flowing into a body input
   port, or back out of the body, admit under the composition's
   **call-site name**. A budget exceedance at either site surfaces as a
   bare `MemoryBudgetExceeded` whose `node` is the call-site identifier
   (e.g. `enrich_call`), carrying whichever `detail` the shared
   node-buffer admission path produced.
2. **Body-interior admit (wrapped error).** An admit failure inside a
   body operator surfaces wrapped in `CompositionBodyError
   { composition_name, inner }`. The inner `MemoryBudgetExceeded.node`
   names a body-internal operator the author never wrote in their YAML
   (e.g. an internal `stage_split` Transform), so the wrapper supplies
   the call-site name on top for attribution.

Consumers pattern-matching on `MemoryBudgetExceeded` catch shape (1) but
miss shape (2); consumers matching only `CompositionBodyError` catch (2)
but miss (1). Match both to catch every composition-involved failure.
