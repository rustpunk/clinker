# Error E310: a memory request could not be granted after spilling freed nothing

## What it means

A node asked for more memory, the memory the run already held filled
`memory.limit`, and the engine's attempt to make room freed nothing.

The engine keeps one account of the memory it holds for the run: every
buffer of rows, join build side, group table and staged output asks before it
grows, and what it is granted is **charged** against `memory.limit`. When a
request does not fit, the engine does not fail at once. It first makes room:
it spills to disk the state that can be written there, in the run's spill
order. E310 means that round freed nothing and the request still did not
fit. The run stops rather than letting the process run out of memory.

Pausing a Source is separate from that round. Under `backpressure: pause`
(the default) or `both`, the engine pauses a Source when the charged total
passes 80% of `memory.limit`, so it reads no further until memory is freed.
A pause frees nothing the run already holds: the rows the Source has read
stay charged until the steps holding them pass them on, write them out, or
spill them.

The diagnostic names the node that asked, what the memory was for and how
much it needed, then shows who holds the memory, what the round tried, and a
limit that would have granted the request. When a single request needs more
than the whole limit — or more than the limit leaves beside state that cannot
spill — the headline says so, and says that spilling cannot help. The rows a
Source has read never count as state that cannot spill, while it reads and
after it has finished reading, when they show as memory not held by any one
node: spilling the steps that hold them frees them.

A well-tuned pipeline rarely sees E310: most state spills to disk long before
the limit fills. E310 means what fills the limit could not be spilled when the
request was made, or could not be spilled any further.

Memory the process uses that the engine does not account for — its own code,
allocator overhead, memory a host application holds — is not charged. Some
long-running steps still also check the process's own memory as the operating
system reports it, and stop the run with E310 when that is over
`memory.limit` even though the charged total is not. That report says so in
its headline; see [When the headline names process
memory](#when-the-headline-names-process-memory).

## Example

E310 is a runtime condition, so it carries no source span and no
`error[E310]` header — the code appears at the start of the message itself
(after the composition's name, when the request was refused inside a
composition; see [Composition involvement](#composition-involvement)):

```
E310 "totals": needed 2.0 MiB more for group state, but only 704.0 KiB of memory.limit 8.0 MiB was left
  charged 7.3 MiB of 8.0 MiB (91%) · private memory 200.0 MiB
  largest holders:
    "enrich"  join build side  3.5 MiB  cannot spill
    "totals"  group state  1.0 MiB  requester
    "sorted"  rows buffered between "orders" and "sorted"  1.0 MiB  in use
    "orders"  rows read from the source  768.0 KiB  paused source
    "dedupe"  decision state  256.0 KiB  cannot spill
    +2 more holders  192.0 KiB
    not held by any one node  640.0 KiB
  reclaim: none attempted
  fix: raise the limit to at least 10M — the smallest limit with room for this request and what the run already holds; later stages may need more
    pipeline:
      memory: { limit: "10M" }
    or: --memory-limit 10M
  remedy: "enrich"'s join build side holds 3.5 MiB and could not be spilled; see "Join build side" in clinker explain --code E310
  See: clinker explain --code E310
```

Grep CI logs for `E310`, not `error[E310]`. The headline starts
`E310 "<node>":`, with the name of the node that asked in double quotes, or
`E310:` alone in a report that names no node.

Read it top to bottom:

- The **headline** names the node that asked (`"totals"`), what for (`group
  state`), how much more it needed and how much of the limit was left
  (`none of memory.limit ... was left` when nothing was). After a reclaim
  round it adds `and nothing more could be spilled`; a report whose reclaim
  line says `none attempted` never claims that, because nothing was tried.
- A **group** line follows the headline when one Reshape or Cull group is too
  large to hold whole. It names the group by the Source and row number of its
  first row, never by its key. When that row was not read from a Source (a row
  an earlier node made), there is no Source to name it by, and the report has
  no group line.
- A **join partition** line follows the headline when a join stopped while
  matching a part of its build side it could not split any further. It
  estimates how many distinct join keys that part held; see [Join build
  side](#join-build-side).
- The **charged** line is the memory the run held at that moment against the
  limit. The private-memory figure beside it is the whole process's memory
  that no other process shares, for comparison; it is not what the limit
  counts.
- **largest holders** lists up to five nodes by what they hold, then one line
  for the rest and one for memory the run holds as a whole (such as output
  staged for writing, and rows a Source that has finished reading still has
  in later steps). Each holder carries its state:
  - `cannot spill`: the engine had no way to spill this memory when the
    request was made. Some state never spills, such as Cull's decision state;
    other state cannot be spilled at some points in the run, such as an
    Aggregate's group state while it produces its results.
  - `at its floor`: it spilled what it could and holds the least it can work
    with.
  - `paused source`: a Source that was paused; the rows it had already read
    are still held.
  - `active source`: a Source still reading; the rows it has read stay
    counted here until the steps holding them pass them on, write them out,
    or spill them.
  - `requester`: the node that asked.
  - `in use`: its memory can spill, but it was in use when the request was
    made.
- **reclaim** says which holders the engine asked to spill, how much that
  freed, and which Sources were paused when the run stopped. The round itself
  never pauses a Source (see [What it means](#what-it-means)). `none
  attempted` means no round ran, in one of three cases:
  - the request was made where the engine cannot spill the run's state: a
    Source reading ahead, output staged for writing, or a join matching its
    rows on a thread of its own;
  - the request alone was larger than the whole limit, so no spill could
    make room for it. Any such request runs no round; examples are a sort
    merging what it spilled, a window's index, a range join's loaded block
    pair or the matches it collects for one row, an Aggregate's single input
    row, and a Reshape or Cull group too large to hold whole;
  - Cull's per-group decisions did not fit beside everything else the run
    held. They cannot spill, and Cull checks them without a round.

  A join checks the run's limit as it goes while it matches its rows,
  whichever way it joins. While it reads its build side, it depends on how
  it joins:
  - a join that keeps the build side in one table in memory checks the limit
    as it builds that table;
  - a join that splits the build side into partitions does not check while
    it reads. When memory runs high it spills its largest partition to disk,
    and it checks the limit when it builds a table for each partition still
    in memory;
  - a join that sorts both sides spills them as it sorts, and checks the
    limit only once it matches.

  When a check finds the run over the limit, or finds that a table would not
  fit, the engine first runs a round to spill other steps' state, and stops
  only if that round could not make enough room.

  Either way the headline does not say that nothing more could be spilled.
- **fix** is the smallest limit with room for this request and what the run
  already holds, in the YAML and command-line spellings. A report with no
  request of its own (see [When the headline says the run held more than the
  limit](#when-the-headline-says-the-run-held-more-than-the-limit)) gives the
  smallest limit with room for what the run already holds.
- **remedy** names the largest holder that cannot spill (or is at its floor)
  and the section below that covers it. A Source is never the remedy, paused
  or active: its rows are relieved by spilling the steps that hold them, or
  by the limit on the `fix:` line. When no holder is to blame because one
  request is larger than the limit, it names the section for what the node
  that asked was holding.
- **spilling cannot help** follows when everything charged is state that
  could not be spilled when the request was made; a Source's rows never count
  toward it, including after the Source has finished reading.

### When the headline names process memory

The engine's charged total is one reading of the run's memory. The other is
the process's own memory as the operating system reports it: the highest
resident memory the engine has read for the process, which also counts memory
the engine does not charge. While some long-running steps, such as a join
matching its rows, still check that second reading, they stop the run with
E310 when it passes `memory.limit`. Spilling cannot lower a reading that is
the highest the process has reached, so no round runs for it. The report then
says which reading was over:

```
E310 "enrich": process memory peaked at 12.0 MiB resident, over memory.limit 8.0 MiB, while "enrich" held join build side; the run had charged 3.0 MiB
  charged 3.0 MiB of 8.0 MiB (37%)
  largest holders:
    "enrich"  join build side  3.0 MiB  cannot spill
  reclaim: none attempted
  fix: raise the limit to at least 12M — process memory reached 12.0 MiB; later stages may need more
    pipeline:
      memory: { limit: "12M" }
    or: --memory-limit 12M
  remedy: "enrich"'s join build side holds 3.0 MiB and could not be spilled; see "Join build side" in clinker explain --code E310
  See: clinker explain --code E310
```

- The **headline** gives the process reading and the limit it passed, the
  node that was working and what it held, and what the run had charged. The
  charged total can be well below the limit: the limit was not full.
- The **charged** line and the holder list are the same account as in the
  other form: what the engine held when the step stopped.
- **fix** is the process reading rounded up to a whole MiB: a limit that
  reading would not have passed.

The gap between the two readings is memory the engine does not charge.
Raising the limit to the printed figure clears the error; shrinking what the
named node holds also lowers the process's memory.

### When the headline says the run held more than the limit

A join checks the run's memory as it works, not only when it asks for more.
Memory that grew without asking first, such as the rows a join has matched so
far, can leave the run holding more than the limit. When
that check finds the charged total over the limit, the engine runs a round to
spill other steps' state first. If the round cannot bring the run back under
the limit, the run stops, and the headline states what the run held rather
than a request, because the step asked for nothing more:

```
E310 "enrich": the run held 9.0 MiB, over memory.limit 8.0 MiB, while "enrich" held join build side and nothing more could be spilled
  ...
  fix: raise the limit to at least 9M — the smallest limit with room for what the run already holds; "enrich" and later stages may need more
    pipeline:
      memory: { limit: "9M" }
    or: --memory-limit 9M
```

Without a round, as when the check runs on a join's own matching thread, the
headline ends at `held join state` and the reclaim line says `none
attempted`. If the round makes room but the process's own memory is still
over the limit, the report takes the process-memory form above instead. The
suggested limit on the `fix:` line is what the run held, rounded up. It
names the step that stopped, because that step was still growing when it
checked: give it room beyond the figure if you can.

## How to fix

### 1. Raise the limit to the printed floor

**Raise `memory.limit`** to at least the figure on the `fix:` line, if the
host has the memory. It is the only remedy that never changes your output:

```yaml
pipeline:
  memory: { limit: "10M" }
```

or, for one run:

```
clinker run pipeline.yaml --memory-limit 10M
```

The figure is a floor, not a recommendation: it is the smallest limit with
room for this request and what the run already held. Later stages of the same
run may need more, so leave room above it.

The suffix must be a bare `K`, `M`, or `G` (binary units). Spellings like
`4GB` or `4 GiB` are **not** accepted. If the limit the diagnostic reports is
not the figure you configured, your `memory.limit` did not parse as written —
re-check it against that grammar before raising anything, since the run is
enforcing a limit you did not set.

A test, or a debug build of clinker run with a test ledger capacity, can hold
a run below `memory.limit`. Its report names `the test ledger capacity` where
this page shows `memory.limit`, and its `fix:` line raises that capacity,
without the YAML and `--memory-limit` lines, which would not lift it.

### 2. Shrink the state that cannot spill

The `remedy:` line names the section that applies. Each covers one kind of
state; the holder list names it the same way.

#### Join build side

A join (a Combine) holds its build side in memory while it matches the other
input against it; the holder list shows it as `join build side` or `join
state`.

1. **Choose the driver deliberately.** When the join's semantics permit it,
   drive with the larger input so the smaller input builds the hash side:
   ```yaml
   - type: combine
     name: enrich
     input:
       orders: orders
       products: products
     config:
       drive: orders                     # large probe/driver input
       where: "orders.product_id == products.id"
       match: first
       on_miss: null_fields
       propagate_ck: driver
       cxl: |
         emit order_id = orders.id
         emit product_name = products.name
   ```
   `drive:` also controls which input is iterated and can change row
   cardinality and ordering. Do not switch it solely to clear a memory error
   without verifying that the resulting join is the one you intend.
2. **Pre-filter the large input** with an upstream `transform` so fewer
   rows reach the probe side.
3. **Narrow the predicate.** A band or inequality join spreads work
   across disk-backed blocks, but one indivisible block pair must still
   fit the limit on its own.

An equality join whose build side spills splits it into partitions by the
join key, and splits a partition that is still too large again. When the join
stops while matching a partition that could not be split further, a `join
partition:` line after the headline estimates how many distinct join keys
that partition held. The two cases call for different fixes:

- `join partition: about 48210 distinct keys` — many keys landed in one
  partition. Raise `memory.limit`, or reduce the rows or columns that reach
  the build side.
- `join partition: about 1 distinct key; one key's rows cannot be split
  across partitions, so repartitioning cannot make them fit` — one join key
  carries the partition's rows. No partitioning separates rows that share a
  key. Raise `memory.limit`, or, if the join's semantics allow it, reduce that
  key's rows before the join (filter or pre-aggregate them upstream).

The figure is an estimate, typically within about 13% of the true count, and
is counted without keeping any key; the report never prints one.

A join listed as `cannot spill` could not be spilled at that point in the
run; raise `memory.limit` to the figure on the `fix:` line.

#### Group state

An Aggregate's per-group accumulators. Group state spills to disk as the
table grows, so it fills the limit only when what cannot spill fills it
alongside, or when one group's state is too large on its own.

Group state listed as `cannot spill` could not be spilled at that point in the
run, for example while the Aggregate produces its results; raise
`memory.limit` to the figure on the `fix:` line.

An Aggregate whose `group_by` leaves out a field of its input's correlation
key keeps its groups in memory for the whole run, so that a failure found
later can still correct them. Its group state is listed as `cannot spill`
from the first row it reads
([#1288](https://github.com/rustpunk/clinker/issues/1288) tracks letting it
spill). Raise `memory.limit`, or add the missing correlation-key fields to
`group_by` if the finer grouping is the one you meant.

An aggregate that keeps `min`, `max`, or another value-buffering
binding holds each contributing row's values until the group finalizes. If a
**single input row's** buffered values are larger than the whole limit, the
headline says one request needs more than the limit can hold: spilling cannot
help, because re-reading it would repeat the overflow. The limit is almost
certainly far too low for the record shape.

#### Rows held for Reshape groups

Reshape applies its rules against a *whole* group at once (every rule sees
the same original rows), so one group must fit even though cross-group and
ingest-time peaks spill. A group larger than the limit has no representation
within it: the headline says one request needs more than the limit can hold,
and a `group:` line names the group by where its first row came from, for
example `group: the one whose first row is row 4812 of source "orders"`. The row
number is the one the dead-letter output writes in `_cxl_dlq_source_row`. The
report never prints the group's key, which is a record value. When the
group's first row was not read from a Source (a row an earlier node made),
there is no Source to name it by, and the report has no `group:` line.

A node that declares `partition_by: []` puts every record in one group, so
the entire input has to fit at once; there is no key to narrow.

A group keyed `null` collects every row whose partition value cannot be a
key: a missing column, an explicit null, an empty string, or an array- or
map-valued cell. Any of those may be inflating it, so look for all of them,
not only for blanks. (A NaN is its own group, not the null group.)

Raising `memory.limit` clear of the figure the headline needs is the only fix
that leaves your output unchanged. Treat that figure as a floor: finalize also
holds the run's remaining groups. Two other levers shrink the group but
**change your results**, so weigh them deliberately rather than reaching for
them to clear the error:

- Dropping columns the node does not read, in an upstream Transform, shrinks
  each record, but Reshape writes every input column through, so those columns
  leave the output too.
- Narrowing `partition_by` redefines the group the rules evaluate against and
  changes results. Declaring fields in an empty `partition_by` does the same.

#### Rows held for Cull groups

Cull evaluates its `drop_group_when` predicate against a *whole* group at
once, so one group must fit even though cross-group and ingest-time peaks
spill. A group larger than the limit is reported as for Reshape: the headline
says one request needs more than the limit can hold, and the `group:` line
names the group by the Source and row number of its first row. As for
Reshape, a group whose first row was not read from a Source has no `group:`
line.

A group keyed `null` holds both the rows with an explicit null and the rows
missing the column entirely; either may be inflating it.

Raising `memory.limit` clear of the figure the headline needs is the only fix
that leaves your output unchanged. Treat it as a floor: finalize also holds
the remaining groups and the per-group decisions. The two result-changing
levers are the same as for Reshape, with Cull's consequences:

- Dropping columns the node does not read, in an upstream Transform, shrinks
  each record, but Cull writes every input column through, so those columns
  leave the output too.
- Narrowing `partition_by` changes what `drop_group_when` counts and changes
  which rows are removed.

#### Decision state

State a routing or filtering decision keeps between records. For a Cull
node it is the per-group drop decisions: they are `O(distinct groups)` and
cannot spill. With too many groups, raise `memory.limit`, or coarsen the
partition key **if** the coarser key is the grouping you actually meant.

#### Window index

An analytic window builds a projected copy of the rows it reads, and an index
over them, rooted at the node its partition names. The copy already keeps only
the fields the window's partition, ordering and expressions need;
`clinker run --explain` prints that field set and its estimate.

Raise `memory.limit`. If the calculation allows it, reducing the rows that
reach the rooted node or simplifying the window so it references fewer fields
also shrinks the index, but either edit can change the calculated result and
must be treated as a pipeline-logic change.

#### Rows buffered between two steps

Rows handed from one node to the next (`rows buffered between "split" and
"totals"`; when several nodes read the same rows, each is named: `rows
buffered between "split" and "a", "b"`), rows collected so a node can scan
all of them (`rows collected for a full scan`), rows parked until a later
part of the pipeline commits (`rows held between "split" and "totals" for
commit`), rows held for a correlation group, and rows collected for
sorting.

Buffered rows spill; a node that reads them scans them one at a time. The
state that fills the limit here is usually a node that must collect the whole
scan into memory at once, beside what else is held.

Raise `memory.limit`, reduce the rows or columns reaching that node, or
choose a streaming topology when the operation does not require every row in
memory at once.

#### Held failing rows

With document-granularity dead-lettering, a failed document's failing rows
are held until the document is rejected (`held failing rows of a failed
document`), and the engine keeps a compact record of the rows it has already
dead-lettered (`set of rows already dead-lettered`). Held rows spill; the
record of written rows cannot. Raise `memory.limit`, or reduce how many
documents fail at once.

#### Rows held until their document is decided

With document-granularity dead-lettering (`dlq_granularity: document`), an
Output writes a document's rows only once the run knows the document did not
fail, so it holds every row of a document until the document closes (`rows
held until their document is decided`). These rows are not failing rows: a
document none of whose rows fail is held the same way. They spill to disk
when memory runs short. Raise `memory.limit` to at least the figure on the
`fix:` line.

## Technical context

**Charged** memory is the engine's own account of what the run holds: each
node's retained state, plus memory granted to the run as a whole (such as
output staged for writing). A request is granted only when it fits beside
what is charged. The private-memory
figure is read from the operating system and also counts memory the engine
does not account for; it is shown for comparison only.

When a request does not fit, the engine runs a **reclaim round**. Each pass
asks the holders that can spill, in the run's spill order (which weighs what a
spill would free) with the node that asked last, and retries the request after
it. The round
continues while a pass frees memory; the request is refused only after a pass
freed nothing and a final pass freed nothing too. The round never pauses a
Source: a Source is paused separately, when the charged total passes 80% of
the limit, and a pause frees nothing already charged. Some refusals run no
round, and their reports say `reclaim: none attempted`: a request made where
the engine cannot spill the run's state (a Source reading, output staged for
writing, a join matching on a thread of its own), a piece of a step's state
larger than the whole limit, and Cull's per-group decisions (see **reclaim**
above). Only a report that carries a round says that nothing more could be
spilled.

Every figure in the report comes from one reading of the account taken at the
refusal. The listed holders, the `+N more holders` line and the `not held by
any one node` line add up to the charged figure exactly. A holder's figure is
what it holds itself plus memory granted in its name.

The suggested limit is a **floor**: charged plus requested, rounded up to a
whole MiB. It grants this request and nothing more; later stages may need
more. When the run already held more than the limit and asked for nothing
more, the floor is what it held, rounded up. When the process's memory was the
reading over the limit, the floor is that reading rounded up instead: no
request was measured, and a limit below the reading would stop the run again
at the same point.

## Composition involvement

A composition (a reusable sub-pipeline included via `use:`) shares the
**same** memory account as the parent pipeline, for operators executed inside
the body and for records admitted back into the parent after the body
returns. There is one limit per run. Records entering a body stay charged as
ownership moves into the body; they are not dropped from the account or
charged twice.

For E310 failures that arise during composition execution, where the report
appears depends on where the request was refused:

1. **Body output (plain report).** Records returning from the body are held
   under the composition's **call-site name**. A refusal there is an
   ordinary E310 that names the call site, for example
   `E310 "enrich_call": ...`. When the call takes back rows its input or its body
   buffered for it, the report names them as rows buffered between the node
   that produced them and the call site.
2. **Inside the body (prefixed report).** A refusal inside the body names a
   node inside the composition that you never wrote in your YAML (for
   example an internal `stage_split` Transform), so the message is prefixed
   with the composition's name:
   `in composition "enrich_call": E310 "stage_split": ...`. This holds for
   every refusal inside a body, including one reported together with other
   errors.

Both shapes are the same E310. To find every E310 in a log, search for
`E310` anywhere in the line, not only at its start.
