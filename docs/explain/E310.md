# Error E310: a memory surface exceeded the hard memory limit

## What it means

At runtime, one of the engine's memory surfaces crossed the hard limit
set by `memory.limit` and could not spill its way back under. The run
aborts rather than letting the process get OOM-killed.

E310 is the engine-wide memory-budget code, not a per-operator one. Many
different surfaces raise it — join hash tables, grouped record buffers,
analytic-window arenas, inter-stage handoff buffers, and per-operator decision state. **The
diagnostic tells you which one.** Read it before picking a fix:

```
E310 <node>: <category> exceeded budget (<used>/<limit>) [<detail>]
```

- `<node>` is the pipeline node that was holding the memory.
- `<category>` is `arena` (any budgeted allocation) or `node_buffer`
  (the handoff layer between stages).
- `<used>` / `<limit>` are bytes. `<used>` is sometimes one surface's own
  footprint rather than the whole run's, so treat it as a floor for how
  much headroom you need, not a target.
- `<detail>` names the specific surface. This is the part that selects
  your remedy.

A well-tuned pipeline rarely sees E310: most surfaces spill to disk long
before the hard limit. E310 means spilling was impossible, insufficient,
or already exhausted.

## Example

E310 is a runtime condition, so it carries no source span and no
`error[E310]` header — the code appears at the start of the message
itself:

```
E310 drop_big: arena exceeded budget (512000/8192) [one Cull correlation
group [account="BIG"] does not fit; the reported use (512000 bytes) is
that group's reload footprint alone. ...]
```

Grep CI logs for `E310`, not `error[E310]`.

## How to fix

Read the `[detail]` first, then apply the matching remedy.

### Universal first resort

**Raise `memory.limit`** if the host actually has the memory. It is the
only remedy that never changes your output:

```yaml
pipeline:
  memory: { limit: "4G" }
```

The suffix must be a bare `K`, `M`, or `G` (binary units). Spellings
like `4GB` or `4 GiB` are **not** accepted. If the `<limit>` this
diagnostic reports is not the figure you configured, your `memory.limit`
did not parse as written — re-check it against that grammar before
raising anything, since the run is enforcing a budget you did not set.

Raise it clear of the reported `used` figure — in the per-surface cases
below, other state is resident at the same time.

### Combine and join surfaces

Details mentioning `combine`, `grace hash`, `iejoin`, or `sort-merge`:

1. **Choose the driver deliberately.** When the join's semantics permit it,
   drive with the larger input so the smaller input builds the hash side:
   ```yaml
   - type: combine
     name: enrich
     input:
       orders: orders
       products: products
     config:
       drive: orders                     # large probe/driver input
       where: "orders.product_id == products.id"
       match: first
       on_miss: null_fields
       propagate_ck: driver
       cxl: |
         emit order_id = orders.id
         emit product_name = products.name
   ```
   `drive:` also controls which input is iterated and can change row
   cardinality and ordering. Do not switch it solely to clear a memory error
   without verifying that the resulting join is the one you intend.
2. **Pre-filter the large input** with an upstream `transform` so fewer
   rows reach the probe side.
3. **Narrow the predicate.** A band or inequality join spreads work
   across disk-backed blocks, but one indivisible block pair must still
   fit the budget on its own.

### Grouped record buffers (Reshape, Cull)

Details naming a specific `correlation group [...]`. These operators
evaluate rules against a *whole* group at once, so one group must fit
even though cross-group and ingest-time peaks spill.

A group named `[whole input]` means the node declares `partition_by: []`,
so every record forms one group and the entire input has to fit at once.

If the printed group name does not match any value in your input, check
whether your partition column holds integers above 2^53. Integer group
keys are placed on a `f64` grid, which cannot represent every such value
distinctly, so two different ids that far out can land in the **same**
group. The name printing rounded is the visible symptom; the group being
oversized is the consequence. Raising the budget clears the error but
leaves the rules evaluating over a group that mixes rows from more than
one entity — check the group's contents before assuming the size is
legitimate. Keys within 2^53, and string keys of any length, are exact.

Raise `memory.limit`. Two other levers shrink the group but **change
your results**, so weigh them deliberately rather than reaching for them
to clear the error:

- Dropping unread columns upstream shrinks each record, but both nodes
  write every input column through, so those columns also leave the
  output.
- Narrowing `partition_by` redefines the group the rules evaluate over,
  which changes which records each rule sees.

### Operator decision state

Details such as `Cull drop-decision aggregate state` — per-group state
that is `O(distinct groups)` and cannot spill. Raise `memory.limit`, or
coarsen the partition key **if** the coarser key is the grouping you
actually meant.

### Oversized aggregate rows

`a single buffered aggregate row's ... footprint exceeds the whole ...
budget` — one input row is larger than the entire budget, so spilling
cannot help; re-reading it would repeat the overflow. The budget is
almost certainly far too low for the record shape.

### Analytic-window arenas

Details beginning `node-rooted arena build` — an analytic window is building
the projected record arena and secondary index rooted at the named upstream
node. The arena already retains only fields required by the window's
partition, ordering, and expressions; `clinker run --explain` prints that
field set and its estimate.

Raise `memory.limit`. If the calculation allows it, reducing the rows that
reach the rooted node or simplifying the window so it references fewer fields
also shrinks the arena, but either edit can change the calculated result and
must be treated as a pipeline-logic change.

### Handoff buffers

Details such as `node-buffer materialization overlap`, `transient node-buffer
materialization`, or a `cross-region tee admission`. Shared and producer-port
handoff buffers can spill; each consumer scans the immutable backing
sequentially. An E310 here means the named consumer needed to collect that
scan into a resident working vector whose overlap with other live state did
not fit the hard limit.

Raise `memory.limit`, reduce the rows or columns reaching that consumer, or
choose a streaming topology when the operation does not require full
materialization.

## Technical context

The `MemoryArbitrator` runs a dual-threshold budget: a soft limit (0.80
of `memory.limit` by default) triggers spilling in the operators that
can spill, and the hard limit aborts. A separate spike allowance
tolerates brief fan-out bursts. Soft-limit crossings cause spill, not
E310.

Surfaces reach the hard limit by different routes — some poll process
RSS, some track their own charged bytes, some weigh a single allocation
against the whole budget before admitting it. That is why `used` is not
uniformly "the whole run's memory": for a single-allocation refusal it
is that allocation's own size.

The sections above represent every current E310 constructor. The set can grow
as new allocations join the shared memory budget, so the `[detail]` string,
not a memorized list, remains the authority on which surface overran.

## Composition involvement

A composition (a reusable sub-pipeline included via `use:`) shares the
**same** `MemoryArbitrator` as the parent pipeline for operators executed
inside the body and for records admitted back into the parent after the body
returns. There is one budget per run.

The input boundary is a current exception to that contract: records entering
a body are cloned into the body-local buffer without an arbitrator admission,
so that clone cannot raise E310 and is not represented by a section above.
Treat it as a memory-accounting gap, not as evidence that the configured limit
was enforced at composition entry.

For E310 failures that do arise during composition execution, the error shape
depends on where the admit failed:

1. **Body-output admit (bare error).** Records returning from the body admit
   under the composition's **call-site name**. A budget exceedance surfaces as
   a bare `MemoryBudgetExceeded` whose `node` is the call-site identifier (for
   example, `enrich_call`) and whose `detail` names the node-buffer admission.
2. **Body-interior admit (wrapped error).** An admit failure inside a
   body operator surfaces wrapped in `CompositionBodyError
   { composition_name, inner }`. The inner `MemoryBudgetExceeded.node`
   names a body-internal operator the author never wrote in their YAML
   (e.g. an internal `stage_split` Transform), so the wrapper supplies
   the call-site name on top for attribution.

Consumers pattern-matching on `MemoryBudgetExceeded` catch shape (1) but miss
shape (2); consumers matching only `CompositionBodyError` catch (2) but miss
shape (1). Match both to catch every E310 a composition can currently emit.
