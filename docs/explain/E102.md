# Error E102: a composition's input port does not accept the column the call gives it

## What it means

A composition's input port lists the columns the composition needs, each with
a type, under `_compose.inputs.<port>.schema`. Each call checks the rows it
feeds the port against that list. This error means one of the listed columns
is missing from the caller's rows, or has a type the port does not accept.

A port accepts a column when its type is:

- the type the port declares;
- the non-empty form of a `{ nullable: <type> }` declaration: a port that
  declares `{ nullable: int }` accepts an `int` column;
- anything, when the port declares `any` or `{ nullable: any }`.

Nothing is converted at the port. A port that declares `float` does not accept
an `int` column, and a port that declares `int` does not accept a column with
no declared type (`any`): the composition's nodes are checked against the
port's types, and nothing guarantees an untyped column holds that type.

## Example

```yaml
# pipelines/orders.yaml
nodes:
  - type: source
    name: orders
    config:
      name: orders
      type: csv
      path: orders.csv
      schema:
        - { name: order_id, type: string }
        - { name: amount, type: any }      # no declared type
  - type: composition
    name: score
    input: orders
    use: ../compositions/score.comp.yaml
    inputs:
      inp: orders
  - type: sink
    name: out
    input: score
    config: { name: out, type: csv, path: out.csv }
```

```yaml
# compositions/score.comp.yaml
_compose:
  name: score
  inputs:
    inp:
      schema:
        - { name: amount, type: int }
  outputs:
    out: doubled
  config_schema: {}

nodes:
  - type: transform
    name: doubled
    input: inp
    config:
      cxl: |
        emit twice = amount * 2
```

```text
error[E102]: composition "score": input port `inp` declares `amount` as `int`,
but "orders" provides `amount` with no declared type (`any`), so nothing
guarantees its values are `int`
help: declare the type where source "orders" declares the column:
`- { name: amount, type: int }`. A port admits the type it declares, ...
```

## How to fix

Each help gives one fix. A line in it has been tried first: the compiler
binds the call with the fix applied and prints the line only if the call then
compiles without this error and without a new one. When no fix checks out,
the help says in one sentence what to change. The check covers this call
only: another call of the same composition, or another node that reads a
column the fix retypes (a Source `schema:` line changes the column for every
node that reads it), can still fail once the fix is pasted, and the next
compile reports it.

1. **The column has no declared type.** Declare it where the Source declares
   the column, as the help prints: `- { name: amount, type: int }`. If the
   column comes from a Transform, the help prints the line that converts it,
   `emit amount = amount.to_int()`, to write in a Transform between that node
   and the call; point the call's `input:` and the port's `inputs:` entry at
   the new Transform.
2. **The column can be empty and the port says it cannot.** The help prints
   the port line declaring the column nullable,
   `- { name: amount, type: { nullable: int } }`, so the composition is
   checked knowing the value can be empty. It prints it only when the
   composition then compiles: a composition that cannot take an empty value
   gets the sentence instead, and the caller has to provide a value.
   When the column comes unchanged from the input port of a composition that
   holds this call, and that port declares it `{ nullable: <type> }`, the
   error names that port: the enclosing composition is checked at every call
   as if the value could be empty. The help prints that port's line with the
   never-empty type, `- { name: amount, type: int }`.
3. **The types differ.** The help prints the line that converts the column,
   to write in a Transform before the call, as in case 1, or, where no
   conversion exists, says to give the column the port's type before the
   call.
4. **The column is missing.** For a Source, the help prints the `schema:`
   line to add; otherwise it names the node that has to provide the column.
5. **The port reads a Route branch.** A composition input port cannot read an
   output port of a Route or a Cull yet (#888). The help prints a Transform
   that keeps every row (`filter true`) to feed the port from.
6. **The port reads a composition's output port by name.** A call's rows are
   the rows of its composition's first output port, read by the call's name:
   for that port the help prints the `inputs:` entry naming the call. Another
   output port cannot be read yet (#1315); move the nodes that read it into
   the composition.

## Technical context

A composition's nodes are checked against the port, the way a function body is
checked against its parameters: a column the port declares with a concrete
type is checked with that type at every call, so a composition that passes
the check compiles at every call that passes this one. What a call outputs
follows what the caller passed, so a column the composition does not write
reaches the next call with the type it had before this one, and a
`{ nullable: <type> }` port does not make a never-empty column possibly
empty. A column declared `any` is checked with the type the call provides, so
an error over it is specific to that call and names the composition and the
port (`E200`).

The caller's rows enter the composition unchanged. Because nothing converts a
value at the port, the check admits only types whose values are already valid
for the declaration: `int` values are valid `{ nullable: int }` values, but
`int` values are not `float` values, and an untyped column's values are not
known to be anything.

The check runs once per call, against the rows that call feeds the port. A
column the port declares that the composition's enclosing composition does
not declare on its own port is `E169`, not `E102`.
