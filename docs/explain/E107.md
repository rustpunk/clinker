# Error E107: Cycle detected in flat post-expansion graph

## What it means

After expanding all composition call sites and flattening the graph, a
cycle was detected. This refines E003 (pre-expansion cycle detection)
with hierarchical name context showing which composition bodies
contribute to the cycle.

## Example

A composition that (directly or indirectly) references itself:

```yaml
# loop.comp.yaml
_compose:
  inputs:
    data: { schema: [{ name: id, type: string }] }
  outputs:
    data: { schema: [{ name: id, type: string }] }
nodes:
  - type: composition
    name: recurse
    input: data
    use: ./loop.comp.yaml  # self-reference -> cycle
```

## How to fix

Break the cycle by removing the self-referential composition call or
restructuring the pipeline to avoid circular dependencies.

The same code reports nodes inside a composition that read each other in a
cycle, or a node that reads itself. A cycle is reported once, naming every
node on it in the order they are declared:

```text
composition nodes "a" and "b" read each other in a cycle, so neither can
receive a row
help: set `input:` of node "b" to an input port of the composition:
`input: inp`
```

Paste the printed `input:` line into the node the help names. The help picks
the node so that no node is left reading a node the composition names as an
output: here the composition's output is `a`, so `b` changes, and the rows
run from `inp` through `b` to `a`. The line is printed only after the
compiler has bound the nodes on the cycle with it, and it names the first
input port that lets every node on the cycle compile, so the port declares the
columns those nodes use. The check covers the nodes on the cycle: a node
after them that uses a column the port does not declare can still fail once
the line is pasted, and the next compile reports it. A node that reads itself gets the same kind of fix,
its `input:` set to an input port.

When no input port works, or a node on the cycle reads more than one input (a
Merge, a Combine or a composition call), the help prints no line. It names
the node to change and the node it should stop reading:

```text
help: change what node "b" reads so that it no longer reads node "m", which
ends the cycle
```

What such a node should read instead is your choice: a Merge that already
reads an input port would write every row twice if it read that port again.

## Technical context

Cycle detection runs on the flat post-expansion graph, not
the hierarchical representation. `PipelineNode::Composition` boundary
markers are retained as structural no-ops but elided during cycle
analysis. This avoids the false positives and false negatives that arise
from scope-qualified name resolution on hierarchical graphs (a known
issue in Airflow TaskGroup).
