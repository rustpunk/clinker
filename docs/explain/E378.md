# Error E378: a composition body declares a Sink under document-level DLQ

## What it means

A source declares `dlq_granularity: document`, and a composition body used by
the pipeline declares a `sink` node. Document-level dead-lettering guarantees
that no Sink writes a record of a document that is rejected. Clinker keeps that
guarantee by running every Sink after every other node, so each document's
verdict is final before any Sink writes one of its records.

A Sink inside a composition body would run inside its composition's own
dispatch, while the rest of the pipeline is still running, where nothing in the
pipeline's order can hold it back until every document's verdict is final.
Clinker refuses the combination at compile time, so the guarantee holds for
every Sink once body Sinks write (issue #1242). Today a body Sink writes
nothing in a run, so moving it to the pipeline is also how its output gets
written.

## Example

```yaml
# pipelines/orders.yaml
nodes:
  - type: source
    name: events
    config:
      name: events
      type: csv
      path: events.csv
      dlq_granularity: document
      schema:
        - { name: id, type: string }
        - { name: value, type: string }
  - type: composition
    name: enrich
    input: events
    use: ../compositions/audited.comp.yaml
    inputs:
      inp: events
  - type: sink
    name: out
    input: enrich
    config: { name: out, type: csv, path: out.csv }
```

```yaml
# compositions/audited.comp.yaml
_compose:
  name: audited
  inputs:
    inp:
      schema:
        - { name: id, type: string }
        - { name: value, type: string }
  outputs:
    out: shape
  config_schema: {}

nodes:
  - type: transform
    name: shape
    input: inp
    config:
      cxl: |
        emit id = id
        emit value = value
  - type: sink
    name: audit
    input: shape
    config: { name: audit, type: csv, path: audit.csv }
```

The diagnostic points at the body Sink and labels the composition call site:

```text
[E378] composition "enrich" declares Sink "audit" in its body, but source
"events" declares `dlq_granularity: document`, which needs every Sink declared
at pipeline level
```

## How to fix

The help gives one fix. Which one depends on whether moving the Sink to the
pipeline through a new composition output port works for this composition
today.

### When the help prints the move

The help prints the move when all of these hold:

- the pipeline itself calls the composition, not another composition;
- no other composition call uses the same composition file;
- the composition declares at least one output port;
- the body Sink reads the node behind the composition's first output port;
- that node is a node of the composition, not one of its input ports;
- that node is not a Route, a Cull or a composition call;
- no node in the composition other than a Sink reads that node;
- when that node is a Transform, the Sink does not set
  `include_unmapped: false` with an `exclude:` that removes every column the
  Transform emits.

The help then prints each edit ready to paste, with the Sink's own
configuration written out. For the example above it prints:

```text
move Sink "audit" to the pipeline and feed it through a new output port of composition "enrich", so it writes only after every document's verdict is final
1. in `compositions/audited.comp.yaml`, under `_compose.outputs:`, add:
    audit: shape
2. in `compositions/audited.comp.yaml`, remove Sink "audit" from `nodes:`
3. composition "enrich" then has 2 output ports, so read `enrich.out` wherever the pipeline reads `enrich` without a port
4. under the pipeline's `nodes:`, add:
  - type: sink
    name: audit
    input: enrich.audit
    config:
      name: audit
      path: audit.csv
      include_unmapped: true
      include_correlation_keys: false
      type: csv
      options:
        encoding: utf-8
```

Step 3 appears only when the composition had one output port. With two or
more ports, a node that reads the composition must name the port it reads.

**A Sink that writes only the columns a Transform emits.** A Sink that sets
`include_unmapped: false` and has no `mapping:` writes only the columns the
node it reads emits, less the ones its `exclude:` lists. In the body that node
is the one behind the port. When it is a Transform, it emits only the columns
its `emit` statements write. At pipeline level the moved Sink reads the
composition call instead, which also passes through every column the
Transform did not emit, so the same setting would write those columns too.
The help therefore writes the columns the Sink wrote in the body into its
`config:` as a `mapping:`, in the order it wrote them, and the moved Sink
writes exactly those. Any other node behind the port, a Merge or a Reshape
for example, emits every column it carries, as the composition call does, so
the moved Sink writes the same columns with its configuration unchanged and
the help adds no `mapping:`. For a body Sink `audit` with `include_unmapped: false` and `exclude: [flag]`,
reading a node `shape` that emits `flag`, `value` and `id` and passes `extra`
through, step 4 prints:

```text
4. under the pipeline's `nodes:`, add:
  - type: sink
    name: audit
    input: enrich.audit
    config:
      name: audit
      path: audit.csv
      include_unmapped: false
      mapping:
      - id
      - value
      exclude:
      - flag
      include_correlation_keys: false
      type: csv
      options:
        encoding: utf-8
```

**Several body Sinks.** Each Sink gets its own diagnostic. Every help assumes
that every Sink that can move does move, so applying all of them gives one
consistent pipeline. The port count in step 3 is the count after all of those
moves.

**A name already in use.** A new port takes the Sink's name. If an output
already declared under `_compose.outputs:`, or a port proposed for an earlier
Sink, already uses that name, the port takes the name with the first free
suffix: `audit_2`, `audit_3`, and so on. A declared output counts even when it
names no node of the composition. The pipeline Sink follows the same rule against the pipeline's node names
and the Sinks moved before it. Its `config:` `name:` is written to match.

### Otherwise: declare the Sink's work at pipeline level

Otherwise the help names this page as the one next step and says why the move
would not run. Today a composition call carries only the rows of its
composition's first output port to the pipeline. It fails when another node in
the composition also reads that port's node. Issue #1315 tracks this. So the
help gives the next step in each case where one of the conditions above does
not hold:

- a composition called inside another composition;
- one composition file used by several calls (each call would declare the same
  Sink, writing the same output);
- a composition that declares no output port;
- a body Sink that reads a node other than the one behind the first port;
- a first port that reads an input port of the composition directly;
- a first port that reads a Route, a Cull or a composition call;
- a first port whose node another node in the composition also reads;
- a Sink that reads a Transform and sets `include_unmapped: false` with an
  `exclude:` that removes every column the Transform emits (a `mapping:` lists
  at least one column, so none
  can keep the moved Sink from writing the columns the composition passes
  through).

In these cases, copy the composition's nodes into the pipeline in place of the
call:

1. Rename the nodes if a pipeline node already uses the name.
2. Point the nodes that read an input port at the node that fed that port.
3. Replace any `$config` value with the value the call passed.
4. Declare the Sink at pipeline level with its own `config:`, reading the node
   it read in the body.
5. Point the nodes that read the call at the node behind the port they read.

For the example above:

```yaml
  - type: transform
    name: shape
    input: events
    config:
      cxl: |
        emit id = id
        emit value = value
  - type: sink
    name: out
    input: shape
    config: { name: out, type: csv, path: out.csv }
  - type: sink
    name: audit
    input: shape
    config: { name: audit, type: csv, path: audit.csv }
```

### If the Sink must stay in the body

Setting `dlq_granularity: record` on the source lifts this check, and failing
records are then dead-lettered one at a time. But a Sink inside a composition
body does not write in a run yet. Issue #1242 tracks this. So a body Sink is
not a working alternative today.

## Technical context

Under document granularity the compiled plan orders every Sink after every
other node, and the scheduler does not run a Sink until every other node of its
pass has run, whatever the memory estimates. `clinker run --explain` lists the
Sinks last. A composition body is dispatched as one step of that order, and its
nodes, a body Sink included, run inside that step. Sinks inside composition
bodies, including how they are wired to writers and configuration, are tracked
in issue #1242.

Issue #1315 tracks composition output ports: each declared port is to carry the
rows of its own node, whatever else in the body reads that node, through nested
calls too. Until then, a composition call hands the pipeline the rows of its
first declared port.
