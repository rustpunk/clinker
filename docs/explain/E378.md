# Error E378: a composition body declares a Sink under document-level DLQ

## What it means

A source declares `dlq_granularity: document`, and a composition body used by
the pipeline declares a `sink` node. Document-level dead-lettering guarantees
that no Sink writes a record of a document that is rejected. Clinker keeps that
guarantee by running every Sink after every other node, so each document's
verdict is final before any Sink writes one of its records.

A Sink inside a composition body runs inside its composition's own dispatch,
while the rest of the pipeline is still running. Nothing in the pipeline's
order can hold it back until every document's verdict is final, so it could
write a document that a later node rejects. Clinker refuses the combination at
compile time rather than keep the guarantee for only some Sinks.

## Example

```yaml
# pipelines/orders.yaml
nodes:
  - type: source
    name: events
    config:
      name: events
      type: csv
      path: events.csv
      dlq_granularity: document
      schema:
        - { name: id, type: string }
        - { name: value, type: string }
  - type: composition
    name: enrich
    input: events
    use: ../compositions/audited.comp.yaml
    inputs:
      inp: events
  - type: sink
    name: out
    input: enrich
    config: { name: out, type: csv, path: out.csv }
```

```yaml
# compositions/audited.comp.yaml
_compose:
  name: audited
  inputs:
    inp:
      schema:
        - { name: id, type: string }
        - { name: value, type: string }
  outputs:
    out: shape
  config_schema: {}

nodes:
  - type: transform
    name: shape
    input: inp
    config:
      cxl: |
        emit id = id
        emit value = value
  - type: sink
    name: audit
    input: shape
    config: { name: audit, type: csv, path: audit.csv }
```

The diagnostic points at the body Sink and labels the composition call site:

```text
[E378] composition 'enrich' declares Sink 'audit' in its body, but source
'events' declares `dlq_granularity: document`, which needs every Sink declared
at pipeline level
```

## How to fix

Move the Sink to the pipeline and feed it through a composition output port.
In the composition file, remove the `audit` Sink from `nodes:` and add a port
for the node it read:

```yaml
_compose:
  outputs:
    out: shape
    audit: shape
```

Then declare the Sink in the pipeline's `nodes:`, reading the new port and
keeping the body Sink's `config:` unchanged:

```yaml
  - type: sink
    name: audit
    input: enrich.audit
    config: { name: audit, type: csv, path: audit.csv }
```

With two output ports, a node that read the composition by its bare name must
name its port, so `input: enrich` becomes `input: enrich.out`. When the
composition is itself called inside another composition, surface the new port
through each enclosing composition's `_compose.outputs:` up to the pipeline.

Or set `dlq_granularity: record` on the source to keep the Sink in the body and
dead-letter failing records one at a time.

## Technical context

Under document granularity the compiled plan orders every Sink after every
other node, and the scheduler does not run a Sink until every other node of its
pass has run, whatever the memory estimates. `clinker run --explain` lists the
Sinks last. A composition body is dispatched as one step of that order, and its
nodes, a body Sink included, run inside that step. Sinks inside composition
bodies, including how they are wired to writers and configuration, are tracked
in issue #1242.
