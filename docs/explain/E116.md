# Error E116: a channel var declaration is incompatible with its type contract

## What it means

A channel (or group) overlay contains a scoped-variable declaration that is not
type-safe. Two forms are rejected:

- **A different type.** The pipeline declares `$pipeline.batch_label` as
  `string` and the overlay declares it as `int`. The overlay cannot change the
  type: the pipeline's CXL was type-checked against the declared type, so a
  value of another type would reach expressions compiled for the first one.
- **A default that does not match the entry's declared type.** The overlay
  declares `type: int` and gives `default: "none"`. This check applies whether
  the entry overrides a pipeline declaration or adds a new variable. The
  default is the value every read observes until something writes the var, so
  it has to be a value of that type.

```
channel "globex": var $pipeline.batch_label override type mismatch — declared
String, override declared Int
```

An overlay is a customization layer over one pipeline, not a redefinition of
it. An override keeps the pipeline's type. An added variable establishes a new
type contract, including a default that must satisfy that type.

## Example

```yaml
# pipeline/base.yaml — the pipeline declares the var and its type.
nodes:
  - type: transform
    name: tag
    input: orders
    config:
      declares:
        - { name: batch_label, scope: pipeline, type: string }
      cxl: |
        emit $pipeline.batch_label = "spring"
```

```yaml
# channel/globex/base.channel.yaml — rejected: the type disagrees.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    batch_label:
      type: int
      default: 0
```

```yaml
# channel/globex/base.channel.yaml — rejected: this new var's default is not an int.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    retry_budget:
      type: int
      default: "none"
```

```yaml
# channel/globex/base.channel.yaml — accepted: same type, matching default.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    batch_label:
      type: string
      default: "globex-spring"
```

## How to fix

1. **For an override, match the pipeline's declared type.** Look up the
   `declares:` entry on the Transform that owns the var and copy its `type:`
   into the overlay.

2. **Give a default of that type.** `type: int` takes `default: 0`, not
   `default: "0"`; `type: bool` takes `default: false`, not `default: "false"`.

3. **To override a value and nothing else, restate the pipeline's type beside
   it.** `type:` is required on every `vars:` entry — an entry that omits it is
   rejected with ``missing field `type` `` before this check even runs — so
   there is no value-only form. The accepted example above is that shape: the
   pipeline's own `type:`, plus the `default:` the overlay is there to supply.

4. **If the overlay genuinely needs a different type, it needs a different
   var.** Declare a second var under its own name in the pipeline and have the
   overlay set that one. One name cannot carry two types across channels,
   because the pipeline's CXL is compiled once.

## Technical context

Scoped vars are resolved before the executor starts, layering the overlay's
values over the Transform-declared defaults and adding overlay-only
declarations. For an override, the declared type is what the CXL type checker
used when it compiled every `$pipeline.x` / `$source.x` read in the pipeline,
so an overlay arrives too late to change it. For every entry, existing or new,
the default is coerced against the entry's declared type before the value enters
the resolved registry.

This condition previously shared code E107 with the composition-cycle check.
One code cannot answer two questions: `clinker explain --code E107` describes
finding a cycle in an expanded composition graph, which is unrelated to a
channel var declaration and often names machinery the pipeline does not use at
all. The conditions now have separate codes.
