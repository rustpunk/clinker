# Error E116: a channel var override disagrees with the pipeline's declaration

## What it means

A channel (or group) overlay redeclares a scoped variable that the pipeline
already declares, and the two do not agree. Two forms are rejected:

- **A different type.** The pipeline declares `$pipeline.batch_label` as
  `string` and the overlay declares it as `int`. The overlay cannot change the
  type: the pipeline's CXL was type-checked against the declared type, so a
  value of another type would reach expressions compiled for the first one.
- **A default that does not match the declared type.** The overlay declares
  `type: int` and gives `default: "none"`. The default is the value every read
  observes until something writes the var, so it has to be a value of that
  type.

```
channel "globex": var $pipeline.batch_label override type mismatch — declared
String, override declared Int
```

An overlay is a customization layer over one pipeline, not a redefinition of
it. It may supply a *value* the pipeline did not, and it may narrow behaviour
the pipeline left open — but the declaration it overrides stays the pipeline's.

## Example

```yaml
# pipeline/base.yaml — the pipeline declares the var and its type.
nodes:
  - type: transform
    name: tag
    input: orders
    config:
      declares:
        - { name: batch_label, scope: pipeline, type: string }
      cxl: |
        emit $pipeline.batch_label = "spring"
```

```yaml
# channel/globex/base.channel.yaml — rejected: the type disagrees.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    batch_label:
      type: int
      default: 0
```

```yaml
# channel/globex/base.channel.yaml — rejected: the default is not an int.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    retry_budget:
      type: int
      default: "none"
```

```yaml
# channel/globex/base.channel.yaml — accepted: same type, matching default.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    batch_label:
      type: string
      default: "globex-spring"
```

## How to fix

1. **Match the pipeline's declared type.** Look up the `declares:` entry on the
   Transform that owns the var and copy its `type:` into the overlay.

2. **Give a default of that type.** `type: int` takes `default: 0`, not
   `default: "0"`; `type: bool` takes `default: false`, not `default: "false"`.

3. **To set a value and nothing else, restate the declared type beside it.**
   `type:` is required on every `vars:` entry — an entry that omits it is
   rejected with ``missing field `type` `` before this check even runs — so
   there is no value-only form. The accepted example above is that shape:
   the pipeline's own `type:`, plus the `default:` the overlay is there to
   supply.

4. **If the overlay genuinely needs a different type, it needs a different
   var.** Declare a second var under its own name in the pipeline and have the
   overlay set that one. One name cannot carry two types across channels,
   because the pipeline's CXL is compiled once.

## Technical context

Scoped vars are resolved before the executor starts, layering the overlay's
values over the Transform-declared defaults. The declared type is what the CXL
type checker used when it compiled every `$pipeline.x` / `$source.x` read in
the pipeline, so the type is fixed at compile time and an overlay arrives too
late to change it. Accepting a mismatched override would leave expressions
compiled for one type reading a value of another.

This condition previously shared code E107 with the composition-cycle check.
One code cannot answer two questions: `clinker explain --code E107` describes
finding a cycle in an expanded composition graph, which is unrelated to a
channel var declaration and often names machinery the pipeline does not use at
all. The conditions now have separate codes.
