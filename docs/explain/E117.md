# Error E117: a channel var's name shadows a reserved system field

## What it means

A channel (or group) overlay declares a scoped variable whose name is one the
engine already provides in that scope. Builtins win resolution, so accepting
the declaration would leave the overlay value silently unreachable. The
declaration is rejected instead.

The reserved names are fixed per scope:

| Scope | Reserved names |
|-------|----------------|
| `$pipeline` | `start_time`, `name`, `execution_id`, `batch_id`, `total_count`, `ok_count`, `dlq_count`, `filtered_count`, `distinct_count` |
| `$source` | `file`, `row`, `path`, `count`, `batch`, `ingestion_timestamp`, `name` |

```
channel "globex": var $pipeline.execution_id shadows reserved system field
```

The same rule already applies to a pipeline's own `declares:` entries. This
diagnostic is the overlay's half of it: a name the pipeline could not declare
cannot be introduced by a channel either.

## Example

```yaml
# channel/globex/base.channel.yaml — rejected: `execution_id` is the engine's
# own per-run identifier, readable as `$pipeline.execution_id`.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    execution_id:
      type: string
      default: "globex-run"
```

```yaml
# channel/globex/base.channel.yaml — rejected: `path` is the engine's
# per-source input path, readable as `$source.path`.
channel:
  target: ../../pipeline/base.yaml
vars:
  source:
    orders:
      path:
        type: string
        default: "/data/globex/orders.csv"
```

```yaml
# channel/globex/base.channel.yaml — accepted: a name of the overlay's own.
channel:
  target: ../../pipeline/base.yaml
vars:
  pipeline:
    tenant_batch_label:
      type: string
      default: "globex-spring"
```

## How to fix

1. **Rename the variable.** Prefix it with something that names the overlay's
   concern — `tenant_execution_id`, `globex_batch_id` — so it does not collide
   with the engine's field.

2. **If you wanted to read the engine's value, do not declare it at all.**
   `$pipeline.execution_id` and `$source.path` are already readable from any
   CXL expression in the pipeline; declaring them is what makes them
   unreachable.

3. **If you wanted to change an input path, change the Source node rather than
   declaring a scoped variable.** The current `sources:` patch surface does not
   address file matchers. A channel that must replace a Source can use a
   structural `replace` override with the complete Source definition; see
   "Channels & Groups" for the strict replacement shape.

## Technical context

The reserved lists are the members the CXL resolver and runtime bind for
`$pipeline.*` and `$source.*`. A builtin is resolved before a user-declared
variable of the same name, so an accepted overlay value would be silently
ignored.

Rejecting at overlay-resolution time keeps the two halves of the rule in one
place: `declares:` validation and channel-overlay validation both consult the
same per-scope list, so the two surfaces cannot drift apart.

This condition previously shared code E110 with the extraction-boundary check
for a selected node that is not in the execution-plan DAG. One code cannot
answer two questions, and the two conditions have nothing to do with each
other; they now have separate codes.
