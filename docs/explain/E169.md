# Error E169: a composition uses a column its input port does not declare

## What it means

A composition's input port lists the columns the composition needs, under
`_compose.inputs.<port>.schema`. Those are the only columns of the caller's
rows the composition's nodes may use. A call passes the caller's rows into
the composition as they are, so every other column the caller has travels
through the composition untouched and comes out the other side in the same
place, as it would if the composition's nodes were written in the pipeline
itself. The composition just cannot use those columns by name.

This error means a node inside the composition uses a column of the caller's
rows that its input port does not list. Clinker refuses this at compile time,
at every call whose rows carry that column. Otherwise the composition would
work only when called from a pipeline that happens to have that column. A call
whose rows do not carry the column at all fails with the error the node gives
for any column that does not exist (`E203` for an expression), since there is
nothing of that name to read.

A column the composition creates itself, with an `emit` or as an aggregate
result, is the composition's own: later nodes in the composition may use it
whatever the port declares. A Reshape `set` or `overrides` entry does not
create a column: it rewrites one that must already exist, and the rows its
rule does not touch keep the caller's value, so it counts as using the column.

## Example

```yaml
# pipelines/orders.yaml
nodes:
  - type: source
    name: orders
    config:
      name: orders
      type: csv
      path: orders.csv
      schema:
        - { name: order_id, type: string }
        - { name: department, type: string }
        - { name: v, type: int }
        - { name: wt, type: int }
  - type: composition
    name: weigh
    input: orders
    use: ../compositions/weighted.comp.yaml
    inputs:
      inp: orders
  - type: sink
    name: out
    input: weigh
    config: { name: out, type: csv, path: out.csv }
```

```yaml
# compositions/weighted.comp.yaml
_compose:
  name: weighted
  inputs:
    inp:
      schema:
        - { name: v, type: int }
        - { name: department, type: string }
  outputs:
    out: score
  config_schema: {}

nodes:
  - type: transform
    name: score
    input: inp
    config:
      cxl: |
        emit r = v * wt
```

`wt` reaches the composition with the caller's rows, but port `inp` does not
declare it:

```text
[E169] composition "weigh" uses column `wt` in node "score", but its input
port `inp` does not declare `wt`. A composition may use only the columns its
input ports declare; every other column passes through the call unchanged.
```

## How to fix

Declare the column on the port. The help prints the declaration to add, with
the column's type at this call, spelled so the call accepts it (a column that
can be empty is printed as `{ nullable: <type> }`):

```yaml
# compositions/weighted.comp.yaml
_compose:
  inputs:
    inp:
      schema:
        - { name: v, type: int }
        - { name: department, type: string }
        - { name: wt, type: int }
```

Every call of the composition then has to provide `wt`. A call whose input
does not have it fails with E102, which names the call and the missing
column.

If the composition should not depend on the column, change the node so it
does not use it.

## Technical context

The composition's nodes compile against the rows the call feeds each port,
in the caller's column order, with every column the caller's rows carry. That
is what makes a call behave as its nodes written inline: an aggregate inside
the composition reads the column it names, wherever the caller keeps it. The
port's schema is checked against the caller's row at each call (E102) and is
the list of names the composition's nodes may use.

Each column of the row the composition binds against carries a mark: the
port it came through and whether the port declares it, or that the column is
the composition's own. A column with no mark is not nameable, so a row built
without its marks refuses names rather than admitting them. The compiler's
name lookup refuses a column whose port does not declare it, which covers
expressions and every check that looks a name up on the row (`group_by`,
`partition_by`, `order_by`, Reshape `set` targets). The names an expression
uses outside name lookup (`distinct by`, positional window calls, qualified
references such as `a.wt`), a Combine's `input.field` references, Reshape
`overrides` names, a window's `group_by` and `sort_by`, log `fields`,
validation `field`, a Sink's `mapping`, `exclude`, `sort_order` and
`split.group_key`, and the columns a nested composition's own ports declare
are each checked against the same mark by a check of their own. The marks
travel with the columns through every node that passes them on, a nested
composition included. A node that writes a column of the
same name, with an `emit` or an aggregate result, makes it the composition's
own from there on. When the composition writes such a column to its output,
the compiler warns with W101, because the composition's value replaces the
caller's.

The nodes are bound in the order they read each other, whatever order the
file lists them in; a node on a cycle is `E107` and an `input:` naming nothing
in the composition is `E004`. A column the port does not declare is also never
offered as a "did you mean" suggestion or listed as available for a
misspelled name.
