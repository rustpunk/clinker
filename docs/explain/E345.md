# Error E345: unknown record-type discriminator in a multi-record flat file

## What it means

A multi-record CSV or fixed-width source streams one record per line and uses a
**discriminator** — a byte range (fixed-width) or a named column (CSV) — to
decide which declared record type each line belongs to. E345 fires when a line's
discriminator value matches none of the `records:` entries the source declares.

A genuinely undeclared discriminator value is a malformed row or a missing
record-type declaration. Under `fail_fast` the run aborts at the offending
line. Under `strategy: continue`, the default record granularity dead-letters
only the unmatched row and continues with the next physical row. A source that
sets `dlq_granularity: document` instead treats the mismatch as an envelope-
integrity failure that condemns the whole file and continues with remaining
files.

```
E345 line 3: unknown record-type discriminator "X" — no `records:` entry
declares this tag. Declare a record type with `tag: X`, use
`error_handling.strategy: continue` with record-grained DLQ to reject only this
row, or set `dlq_granularity: document` to dead-letter the file.
```

## Example

```yaml
# A payment file with header (H), detail (D), and trailer (T) record types.
# A line whose first byte is `X` matches no declared type → E345.
nodes:
  - type: source
    name: payments
    config:
      name: payments
      type: fixed_width
      glob: ./*.txt
      schema:
        discriminator: { start: 0, width: 1 }
        records:
          - { id: header,  tag: H, columns: [ { name: batch_id, type: string, start: 1, width: 9 } ] }
          - { id: detail,  tag: D, columns: [ { name: amount,   type: int, start: 1, width: 9 } ] }
          - { id: trailer, tag: T, columns: [ { name: count,    type: int, start: 1, width: 9 } ] }
```

```text
HBATCH0001
D000000100
Y000000999      <- discriminator "Y" matches no record type → E345
T000000001
```

## How to fix

1. **Declare the missing record type.** Add a `records:` entry whose `tag`
   equals the unmatched discriminator value, with the fields that type carries.

2. **Correct the file** when the value is a corruption or a stray line — the
   discriminator must sit at the configured byte range / column on every line.

3. **Dead-letter only the row** with `error_handling.strategy: continue`, a
   configured DLQ, and the default `dlq_granularity: record`. The DLQ entry's
   `record_type` is the unknown tag. `_cxl_dlq_source_record` carries the fixed-
   width line text or a JSON array of decoded CSV cells, so Clinker preserves
   the rejected input without pretending it matched a declared field layout.

4. **Dead-letter the file** by setting `dlq_granularity: document` (with a
   `continue` error strategy) on the source, so the entire file is condemned
   and the run continues with the other files.

## Technical context

The multi-record reader builds a `tag → record type` map at startup from the
source's `records:` list and a static superset schema whose lead `record_type`
column carries the matched type's id. For each physical line it extracts the
discriminator value, looks up the type, and streams one record on the superset
schema — never buffering the file. A lookup miss is E345, classed as a
typed unknown-record failure — distinguishable from both a trailer **count**
mismatch and body-after-trailer validation. The reader returns the decoded row
with E345 after consuming exactly that row, so record-grained `continue` can
route it through the bounded source-attempt/DLQ path and resume. Under
`dlq_granularity: document` the same typed failure condemns the whole file —
every already-streamed record of that file is rejected with it. The physical
line number in the message counts every line including any header, trailer, or
skipped blank.
